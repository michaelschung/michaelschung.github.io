Instagram authorize()

instagram.service.ts lines 2984 – 3175

This method is the core of Instagram account connection. When a creator clicks "Connect Instagram" in the studio, Instagram redirects back with an OAuth code. authorize() exchanges that code through a three-step token dance (short-lived → long-lived → profile fetch), upserts a TeamInstagramAccount record, stores the token in AWS Secrets Manager, provisions free credits, subscribes to webhooks, and bootstraps default DM automations.

Key Concepts

TermMeaning
appScopedUserId Instagram's app-scoped user ID — unique per IG account per app. Used as the primary dedup key to prevent the same IG account being linked to two teams. Sourced from the id field on the /me response (a JSON string, safe from precision issues).
instagramId Instagram-scoped user ID (user_id from /me). A separate identifier used for API calls like webhook subscriptions (POST /{instagramId}/subscribed_apps).
shortLivedToken Ephemeral token (∼1 hour) returned from the OAuth code exchange. Immediately swapped for a long-lived token.
longLivedToken Durable token (∼60 days) stored in Secrets Manager. Used for all subsequent Instagram API calls.
MetaTemplateEnum Predefined DM automation templates (Giveaway, Bio CTA, Story DM, Comment Keyword, etc.) auto-created on first connect.

Code Walkthrough

1. Permission Check  L2993 
await this.authCheckAndGetTeamIgAccount({ teamId, requesterUserId, noThrow: true });

Verifies the requesting user is a team member/owner/admin and that the team's plan supports Instagram (PlanGroup.BETTER_THAN_GOLD). The noThrow: true flag means it returns null instead of throwing if no TeamInstagramAccount exists yet — expected on first connect.

2. Short-Lived Token Exchange  L2997–3031 
POST https://api.instagram.com/oauth/access_token
{
  client_id, client_secret,
  grant_type: 'authorization_code',
  redirect_uri: 'https://{app|dev}.getpinpoint.io/studio/insta/callback',
  code: trimHashSuffix(accessCode)
}

Exchanges the OAuth authorization code for a short-lived access token. trimHashSuffix() strips a trailing #_ that Instagram sometimes appends to the code.

The redirect URI is environment-aware: app.getpinpoint.io in production, dev.getpinpoint.io otherwise.

3. Long-Lived Token Exchange  L3033–3061 
GET https://graph.instagram.com/access_token
  ?client_secret=...
  &grant_type=ig_exchange_token
  &access_token={shortLivedToken}

Swaps the short-lived token (~1 hour) for a long-lived one (~60 days). Extracts access_token and expires_in (seconds) from the response, then computes expiryDate via dayjs.

4. Profile Fetch  L3063–3090 
GET https://graph.instagram.com/v24.0/me
  ?fields=id,user_id,username,name,account_type,
          profile_picture_url,followers_count,
          follows_count,media_count
  &access_token={longLivedToken}

Fetches the creator's Instagram profile. Two IDs are extracted:

  • data.id → appScopedUserId — app-scoped, used as dedup key (string, safe from precision loss)
  • data.user_id → instagramId — Instagram-scoped, used for API calls like webhook subscriptions
5. Record Upsert & Self-Healing  L3092–3125

This is the most nuanced section. It handles three scenarios:

a) Lookup by appScopedUserId

let teamInstagramAccount = await prisma.teamInstagramAccount
  .findUnique({ where: { appScopedUserId } });

If found and belongs to a different team → throw 422. One IG account per team.

b) Self-healing fallback by teamId

if (!teamInstagramAccount) {
  teamInstagramAccount = await prisma.teamInstagramAccount
    .findFirst({ where: { teamId } });
}

If the appScopedUserId lookup misses (because the existing record has a corrupted or UUID value from historical bugs), falls back to finding by teamId. On re-auth, the record's appScopedUserId gets corrected.

c) Create or update

  • No record found → create new TeamInstagramAccount
  • Record found → update appScopedUserId and instagramId to correct values, then delete any duplicate records for the same team
Why self-healing? Historically, appScopedUserId was taken from the token exchange response's user_id field, which is a JSON number. Instagram user IDs exceed JavaScript's Number.MAX_SAFE_INTEGER, so JSON.parse would silently mangle the value. Different API calls could produce different corrupted numbers for the same account, leading to duplicate records and failed dedup checks. A later fallback to crypto.randomUUID() compounded the problem. The fix: always use data.id from the /me endpoint, which is a JSON string.
6. Secret Storage  L3127–3150

Stores the long-lived token and expiry in AWS Secrets Manager under key {env}-instagram-{teamId}.

{
  accessToken: "...",
  expiresAt: "2026-04-21T...",
  lastNotifiedAt: null
}

Creates the secret if new, updates if it already exists. Then writes the secretKeyName back to the DB record.

7. Free Credits  L3152–3160

On first connection, creates an InstagramFreeCredit record with 100 credits (the default). Skips if one already exists (idempotent for re-auth).

8. Webhook Subscription  L3162 
POST https://graph.instagram.com/v24.0/{instagramId}/subscribed_apps
  ?subscribed_fields=comments,messages
  &access_token=...

Subscribes the IG account to comments and messages webhooks so Pinpoint can receive real-time DM and comment events. This is the page-level subscription (distinct from the app-level subscription configured in Meta's developer console).

9. Automation Templates  L3164–3170

Iterates over all 10 MetaTemplateEnum values and creates a default automation for each:

  • Giveaway, Bio CTA, Story DM, Comment Keyword, Any Comment
  • Welcome, Tag a Friend, FAQ Icebreaker, Buttons, Carousel

Each creation is wrapped in try/catch so a single template failure doesn't abort the whole authorization. These are created via createAutomationFromTemplate() which delegates to template-specific methods.

Side Effects & Gotchas

Historical bug: JS number precision on Instagram IDs Instagram user IDs exceed Number.MAX_SAFE_INTEGER (9007199254740991). The old code read user_id from the token exchange response, which was a JSON number — silently corrupted by JSON.parse. This caused: (1) wrong appScopedUserId stored, (2) dedup check failures leading to duplicate records, (3) the same account appearing linked to "another team" on re-auth. Fixed by sourcing appScopedUserId from /me's id field (a JSON string), with a teamId fallback for self-healing existing records.
Duplicate cleanup is reactive Existing duplicate TeamInstagramAccount records are only cleaned up when a team re-authorizes. Teams that never re-auth will retain their duplicates until manually cleaned.
Secret overwrite on re-auth Re-authorization overwrites the existing AWS secret with a new token and resets lastNotifiedAt to null. Any in-flight API calls using the old token will fail after the secret is updated.
Automation template errors are swallowed Each of the 10 createAutomationFromTemplate calls is wrapped in try/catch. A failure (e.g., template already exists) is logged but doesn't fail the authorization. This is intentional — templates are nice-to-have defaults, not critical to the connection.
